# v0.01 readiness audit: can the pre-alpha be built from the specifications?

Audit date **2026-09-13**, status refreshed **2026-09-14** (final audit), performed by reading every current
specification, checkpoint, research index and the implemented application/engine code in this checkout. This is a documentation review, not an
implementation report or a new set of rulings. It answers one question: could an agent handed this
repository build the [confirmed v0.01 journey](pre-alpha-design-gaps.md#confirmed-first-acceptance-journey)
from the documents alone, and if not, which specific artifacts are missing?

Each gap and finding below has a stable ID so separate agents can claim one, resolve it, and record the
result in the owning specification. Resolving a gap means producing the named artifact or obtaining the
named user decision; it does not authorize inventing rules. The [rules adaptation principles](rules-adaptation-principles.md),
the pinned-Compendium-only research rule in [project instructions](../agent.MD), and the
"ask one question at a time in plain text" convention all apply to this work.

## Verdict

**Current scope checkpoint, 2026-09-14:** the user is satisfied with the reviewed v0.01 shared-
basics scope and wants build-time questions only as needed. The final scope pass found no new
broad product decision requiring another review round. G4 scope and the G6 language choice are
settled; this does not close outstanding G1–G3 contracts, G5 shared-operation detail or G6–G7
engineering/verification. Follow [the build handoff](web-app-build-handoff.md#v001-scope-review-complete--build-handoff).
Do not interpret scope acceptance as evidence that the complete journey has been built or tested.

## 1. Blocking gaps for v0.01

These prevent the second half of the journey. Each names the artifact that closes it.

### G1. Level-one devil Fury decision table

**Missing:** a concrete, sourced list of the creation decisions the minimal wizard must present, in the
Compendium's step order, with option pools, counts/budgets, dependencies, automatic grants and source
references for each. The [wizard spec](character-wizard-spec.md#v001-scope) requires "every applicable
creation step" with one supported option per step; the [hero fixture](hero-fixture.md) supplies one legal
path. Neither is a decision definition an evaluator can consume.

**Artifact:** a `docs/fury-level-one-decisions.md` (name proposed; not present in this checkout as of
2026-09-14) containing, per step from
[Making a Hero](../vendor/steel-compendium/en/unified/md/chapter/making-a-hero.md#step-by-step-hero-making):
stable decision/branch IDs, the selection shape, permitted values or the one supported set, counts and point
budgets, what depends on what, automatic grants, and the SCC references. Cover ancestry (signature trait plus
purchased traits), culture (environment/organization/upbringing/language), career (skills, languages, perk,
inciting incident), class (characteristic array, skills, aspect, ability choices), kit, the optional
complication, and details. State explicitly which steps are optional and what "one supported option" means
for budgeted choices. Owner: rules thread. Depends on F1 below.

**Implementation note, 2026-09-14 (R01):** delivered. `docs/fury-level-one-decisions.md` records every step of
*Making a Hero* in source order with stable ids, shapes, full pools, budgets with quoted source sentences,
dependencies, automatic grants and three worked sets; `shared/content/fury-level-one-decisions.json` mirrors it;
`tests/fury-decisions.test.ts` checks paths, verbatim values and the worked sets. Complication is listed but not
presented (Q-CHAR-1). Remaining source silences are Q-R-100 to Q-R-103. Independent rules review is pending.

### G2. Derived-value formulas and evaluator contract

arithmetic for one build but not the general rule, and the fixture's `Entity` deliberately omits fields.
Also missing is the pure evaluator contract (selections in; complete/incomplete/invalid/unsupported status,
diagnostics and derived baseline with provenance out) requested in
[app status](workstream-app-status.md#integration-dependencies).

**Artifact:** formulas with Compendium references, and the evaluator's input/output shape with three

**Implementation note, 2026-09-14 (R02):** delivered. `docs/character-derived-values.md` gives every formula
(characteristics, Stamina maximum, Recoveries and recovery value, winded, speed, stability, size, disengage,
potencies, heroic resource name and creation value, saving-throw threshold, Renown, Wealth, kit contributions,
granted skills/languages/traits/features/perks/abilities) with the verbatim source sentence and the R01
decision id that supplies it, the provenance rule, the evaluator contract and three hand-computed examples
(complete: the hero fixture reproduces Stamina 30, Recoveries 10, recovery value 10, speed 6, stability 2 and
the rest; incomplete: missing kit; invalid: over-budget traits). `shared/contracts/characterEvaluation.ts`
carries the types only; `shared/content/character-evaluation-examples.json` mirrors the examples and
`tests/character-derived-values.test.ts` checks their quotes and numbers against the pinned files. Live
initialization remains G3 (R03). Rules review is pending.

## 2. Findings: contradictions, errors and unhandled interactions

None of these breaks a confirmed ruling, but each will mislead an implementer or surface as soon as the
named mechanic is automated.

### F1. "Background" is not a creation step

The [wizard spec](character-wizard-spec.md#3-decision-system) lists the foundational choices as
"ancestry, background, career, and class" and [pre-alpha-design-gaps](pre-alpha-design-gaps.md#confirmed-first-acceptance-journey)
repeats it. In the pinned Compendium, [Background](../vendor/steel-compendium/en/unified/md/chapter/background.md)
is the chapter that contains **Culture** and **Careers**; the step list in
[Making a Hero](../vendor/steel-compendium/en/unified/md/chapter/making-a-hero.md#step-by-step-hero-making)
is ancestry, culture, career, class, kit, free strikes, complication, details, connections. Culture and the
optional complication are missing from the wizard's foundational list. The [hero fixture](hero-fixture.md)
uses the correct terms. **Fix:** replace "background" with culture and add the complication step to the
wizard spec and the pre-alpha journey; G1 must follow the source's step list.
**Status:** corrected in the 2026-09-14 final audit; see the diffs of `docs/character-wizard-spec.md`
and `docs/pre-alpha-design-gaps.md`.

### F2. Default-hidden foes cannot be targeted by players

**Resolved for v0.01, 2026-09-14 — foe hiding deferred.** All loaded foes appear in the
player/observer roster, with participating foes visible in shared combat setup and initiative.
No hide/reveal controls or Add visibility setting are required for this milestone. Full stat blocks
remain Director-only; health display and Malice visibility retain their separate policies. See
[the owning visibility contract](table-spec.md#monster-visibility-and-health-display).

The original issue was a default-hidden foe that could attack while remaining unavailable to
player roster targeting. Whether acting reveals it and how hidden initiative is presented remain
future design questions if hiding returns; neither blocks the v0.01 acceptance path.

### F3. Apply-then-revise is only worked out for Lines of Force

**Scope update, 2026-09-13:** automatic response reconciliation is now deferred beyond v0.01;
this finding remains future work before that automation is introduced, not a current milestone gate.

Parry is confirmed as a response card that appears after the hit is applied, and Parry halves damage. The
[dependent-reversal rule](table-spec.md#inline-interaction-cards-in-the-game-log) that reverses invalidated
consequences is stated only for Lines of Force. When automated, a late Parry must reverse winded, dying, and
threshold-based grants such as first-damage-each-round Ferocity, or the user must rule that those stand. The
docs list this as open; it is flagged here because Parry is a core level-one ability and will arrive early.
**Needs:** a user ruling generalizing or limiting dependent reversal for damage-modifying responses.

### F4. Solo nonconsecutive turns versus bottom-of-roster placement

Granted turn entries go into their own group at the bottom of the roster. When the hero side is exhausted and
the remaining side finishes its turns, two bottom groups for one solo would run consecutively, which the
source forbids for solos. The "source timing takes precedence" clause covers it in principle; no document
says how the app enforces it. Not a v0.01 concern (no solo in the fixture). **Needs:** a case ruling when
bosses enter scope.

### F5. Hero-token spend and the early-close rule

The early-close rule closes a character's unused optional *triggered-action* opportunity when they commit an
unrelated ability. Spending a hero token after a failed save is not a triggered action, so whether an
unrelated ability in the gap after End turn closes that token button is unspecified. Minor; deferred with
the token follow-up under G4. **Needs:** a one-line clarification when that follow-up is scheduled.

### F6. Wrap-up deposits versus the character sheet lock

Closeout deposits loot into character inventories, but the sheet lock (which covers inventory edits) is
released only when "the encounter finishes its normal ending procedure." Whether deposits happen inside or
after the lock is already listed as open in the [V1 checkpoint](v1-spec-checkpoint.md#remaining-work-before-complete-v1-play).
Inventory is deferred past v0.01, so this is recorded for completeness only.

### F7. Stale statements a new builder would trust

- [Accounts spec, section 1](accounts-and-access-spec.md#1-current-implementation-and-scope) says the
  checkout has no Convex package, backend schema or account system. All three now exist.
- [Tech stack spec, section 2](v1-tech-stack-spec.md#2-recommended-stack) says the checkout has an npm
  lockfile. It now uses pnpm with the recommended libraries installed.
- [Wizard spec header](character-wizard-spec.md) says neither the wizard nor its campaign workflows are
  implemented. Authored drafts, private notes and saved choice revisions exist; evaluation does not.

**Fix:** update the three passages to describe the current checkout, without implying more is implemented
than [app status](workstream-app-status.md) records.
**Status:** corrected in the 2026-09-14 final audit; see the diffs of `docs/accounts-and-access-spec.md`,
`docs/v1-tech-stack-spec.md` and `docs/character-wizard-spec.md`.
