## Product intent

Build a mobile-optimized companion for the Draw Steel tabletop role-playing game that works independently of a digital battle map.

The intended product includes accounts, character creation and management, campaigns and player invitations, encounter creation and operation, a complete monster glossary, and persistent resource tracking across sessions.

The table is the heart of the app: a shared play space inside a campaign, with participants, an active Director, text chat, sheets, monsters, and real-time rules resolution. Campaign owner and active Director are distinct roles; any participant, including the Director, can have multiple campaign characters. See [the first-pass feature inventory](docs/product-features.md) for account/social features, owned content, public libraries, creation tools, and unsettled suggestions. The first headless combat experiment is implemented; see [its milestone](docs/milestone-1.md) and [review results](docs/milestone-1-review.md). Avoid expanding the application architecture beyond authorized experiments.

A saved encounter is a reusable monster selection plus supporting data. Loading it into a table creates an independent snapshot; the saved encounter and loaded table state do not update each other.

Every character is user-owned and either unattached or attached to one campaign only. Attachment gives the campaign owner and active Director access to the sheet and progression history, with possible private-field exclusions such as player notes still to be defined, and allows campaign operations to connect to values such as Victories and experience. Current direction: build choices remain with the owning user; the Director does not choose options for someone else's character. Characters can be detached for reuse or duplicated as independent characters into another campaign. Campaign values, including XP and Victories, clear on detachment and do not transfer into another campaign; the character retains its current level, build/history, authored details, and inventory. A campaign duplicate starts with cleared campaign values without clearing the original's values. On attachment, choose an entry level up to the character's current level, restoring that progression build and derived stats while retaining inventory. See [attachment requirements](docs/product-features.md#character-ownership-and-campaign-attachment) for remaining permissions and non-campaign live-state questions.

Both the rules engine and the app's game operations must work without the visual UI. A CLI-like interface is an intended development tool: agents can load heroes and monsters, run battles, record inputs and outputs, and inspect actual sheet/state changes. It must exercise the same game operations the UI uses. Verify rules interpretation against Compendium context and separately verify that resolved effects reach stored state. The table UI will be iterated extensively and must not be a prerequisite for this workflow.

The table's central experience is a rolling dialogue/history of what happens there, with the UI layered over headless operations. The game log is a record, separate from the modifiers that produce changes: the rules engine is deterministic and the dice roller is pseudorandom. Record initial game values, each modifier's input before invocation, its output, and the resulting state changes. Moving backward or forward through history restores the recorded state before or after an action without invoking those modifiers again, changing actual game state rather than merely displayed messages. The current [data architecture checkpoint](docs/data-architecture-spec.md) places action-by-action undo inside encounters and realtime shared play inside open sessions. After session closure, detailed history can be compressed and retained alongside smaller current-state, summary, and archive-reference records. Earlier discussion requested rollback across sessions; whether closed sessions can be reopened for live undo remains unanswered after this refinement. Preserve historical detail while that policy is open. Navigation permissions, chat behavior, action boundaries, and continuation after rollback also remain open.

The central architecture is a client-independent Draw Steel rules engine with full spatial rules understanding as an intended capability. The mobile app is a client of that engine. Future clients include a digital battle map and potentially a physical battle map observed through machine vision.

The engine accepts actions, state, and relevant inputs and produces deterministic, structured outcomes. Clients can apply damage, resources, and conditions to stored character and monster state. A client without a digital map can describe spatial outcomes in prose for players to enact; a future map client can consume the same structured outcomes to update its map.

Partial automation is an intended playable mode. The app must handle loading monsters, preparing encounters, and identifying available character abilities while showing the complete ability text alongside what the engine actually applied. Players can complete unsupported effects or correct results through recorded manual game operations. Distinguish applied, manually resolved, and still-unresolved parts; never present partial automation as complete resolution. As parser support improves, the required manual work should shrink. Preserve effect dependencies and prevent double application when automated resolution resumes.

Full spatial rules support must not require every client to maintain a digital map. Missing spatial facts must not be silently invented or treated as false. See [the engine architecture](docs/engine-architecture.md) for confirmed intent and proposed implementation boundaries.

The app is online-first. Full offline operation is not an initial requirement. Convex is the chosen app backend for responsive shared state, including remote play. The engine's language and runtime remain open and must be chosen independently of the app stack.

Treat the engine as a valuable standalone project that other applications and games can consume. A possible future Minecraft-like game using Draw Steel heroes and monsters motivates portability; building that game is not current scope. Preserve the client-independent rules engine boundary when implementing persistence and shared state.

The intended authoring interface is Draw Steel stat-block language: parse mechanics from official content and from homebrew written in supported formulas. Build toward a parser plus reusable rules interpreter. Arbitrary natural-language comprehension is not implied. See [rules language](docs/rules-language.md).

This is a hobby project with limited human development time. Previous attempts failed through invented rules and then excessive verification machinery. Do not introduce vocabulary ban lists, per-rule human approval queues, source-hash proof systems, or process frameworks as substitutes for working behavior. Source references help locate evidence; they do not prove semantic correctness. Prefer a small set of meaningful behavior examples and executable corpus reports generated from the implementation.

## Development approach

- Use [the accounts and access specification](docs/accounts-and-access-spec.md) for regular accounts, early friendship/request/blocking controls, separate admin sign-in, campaign membership and owner-wide bans, exactly one active Director, and session/until-revoked character sharing. Friendship initially grants no content access; friends-only campaign/statistics visibility is future scope. Whether personal blocking also applies campaign bans remains open. Convex Auth is provisional; Better Auth is an accepted alternative if it better meets the requirements. Keep confirmed rules distinct from proposed expiry, privacy, removal, and sharing-scope behavior. This is a specification checkpoint, not backend implementation authorization.
- Use the [3D dice roller adaptation specification](docs/dice-roller-spec.md) for the optional draggable tray. Dice generation, validation, and recording stay in shared code/CLI operations; visual physics presents accepted results and never determines gameplay values. The animation technique remains proposed, and the specification is not an implementation.
- Use the [data structure and architecture specification](docs/data-architecture-spec.md) as the current checkpoint for shared content, user data, encounter journals, session closure, archives, and statistics. It separates confirmed intent from proposed contracts and unanswered decisions; the earlier storage analysis remains supporting research. This is a documentation checkpoint, not authorization to implement or deploy the backend.
- Use [the character wizard specification](docs/character-wizard-spec.md) as the primary implementation reference for creation, advancement, full edits, progression history, campaign review, and interchange. It distinguishes confirmed requirements, proposed implementation contracts, and remaining decisions. Keep it current when character requirements change; foundation/research notes remain supporting evidence.
- Character creation and full editing use the main wizard with foundational choices and access to all levels/options. A scoped level-up wizard uses the same decision system for only the character's level-transition choices. Campaign admission and full edits require Director review/approval before the proposed build takes effect; pending full edits leave the effective campaign build unchanged. Scoped level-ups are not review gated. The user makes choices; the Director approves a revision, not replacement choices. See [wizard modes and review](docs/character-wizard.md#wizard-modes-and-campaign-review). This is a user-requested product workflow, distinct from development-time approval processes.
- Project-authored application code is GPLv3 (`GPL-3.0-only`); see `LICENSE` and `THIRD_PARTY_NOTICES.md` for the distinction from upstream software, game content, and artwork.
- Forge Steel is a pinned Git submodule at `vendor/forge-steel`. Keep it unmodified and do not advance its pin automatically. The character wizard is the current app workstream; use its progression/choice structure as a reference while keeping Steel Compendium as the intended rules-content source. Our UI and character model remain independent design decisions. See [wizard foundation](docs/character-wizard.md) and [dependency guide](docs/forge-steel.md).
- Preserve the ability to import Forge Steel hero data files when designing our character model; exporting compatible files is also desired. Treat this as an interchange adapter, not a requirement to adopt Forge Steel's internal model. See [file-format research](docs/forge-steel-interchange.md) for nested selections, runtime state, and import refresh behavior that can affect round trips.
- Character model direction: a decision matrix/tree supplies the build, supplemented by authored descriptions/flavor and inventory, with a derived stats/abilities layer and changeable play values. Keep the derived baseline distinct from current resources, conditions, and adjustments so recalculation does not reset play state. The proposed dependency-graph representation and remaining state decisions are recorded in [wizard foundation](docs/character-wizard.md#character-model-direction).
- Character progression needs its own restorable history, like the game log: restore any previous recorded decision point (for example level-7 Shadow back to their level-3 build), including the choices and stats derived from them, while retaining present inventory. This is not a whole-character or encounter rewind. See [progression rollback](docs/character-wizard.md#progression-history-and-rollback); live-resource reconciliation and new choices after rollback remain open.
- Steel Compendium is a pinned Git submodule at `vendor/steel-compendium`. Keep upstream files unmodified; consult [the dependency guide](docs/steel-compendium.md) to inspect or adopt updates. Do not automatically advance the pin during builds or startup.
- Use [the Compendium navigation guide](docs/compendium-navigation.md) to find definitions, follow rule references, and recover sourcebook context before implementing mechanics.
- Establish a clear, durable development process suitable for sustained agent-driven work.
- Keep requirements, architectural decisions, rules sources, and acceptance criteria in the project so later work can build on them.
- Verify Draw Steel mechanics against identified, versioned sources rather than inferring them from D&D or memory.
- Track permissions and attribution separately for game content, third-party application code, and artwork.
- Treat community data as an input requiring validation; do not equate successful import with complete or correct rules support.
- Keep proposed architecture and technology choices explicitly provisional until settled.
- Keep CLI and app UI progress coordinated. The user is developing the UI in another thread; keep game behavior in shared operations, communicate contract changes, and use playtest findings to inform both clients rather than growing a separate CLI product.
